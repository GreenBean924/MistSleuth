# AI 剧本杀 DM —— 产品文档

> 一个单人沉浸式剧本杀平台：AI 同时担任主持人、其余角色扮演者和复盘引擎。
> 选一个角色 → 搜证推理 → 指认凶手 → AI 还原真相。

---

## 一、一句话定位

**「选一个角色，由 AI 扮演其余所有角色并主持，沉浸式玩完一整局剧本杀，最后得到一份 AI 复盘。」**

这不是「帮 DM 查资料的问答助手」，而是「玩家直接上手玩的单人侦探游戏」。

---

## 二、要解决的问题

传统剧本杀有三个痛点，本产品逐一对应：

| 痛点 | 本产品的解法 |
|---|---|
| 玩一局要凑 4–8 个真人 + 一个熟读手册的 DM，成本高 | 单人即可玩，AI 演其余角色 + 主持 |
| DM 必须通读数百页手册、记住每条线索归属 | 剧本被 LLM 结构化抽取，AI 主持自动掌握 |
| 玩完没人帮你复盘「我推理错在哪」 | 内置 AI 复盘，对照真相逐条还原时间线、动机、手法 |

**核心难点（也是简历的价值所在）**：剧本杀信息是「上帝视角」全量文本，但玩家只能拥有「单角色视角」。如何让 AI 扮演角色时**不剧透**、**角色一致**，是这个产品真正的技术壁垒。

---

## 三、目标用户与核心场景

- **目标用户**：想玩剧本杀但凑不齐人的玩家；想快速体验一个新剧本的推理爱好者。
- **核心场景**：打开网页 → 选剧本 → 选角色 → 走完「搜证 → 推理 → 指认」→ 看复盘。全程 20–30 分钟。

---

## 四、主要功能（核心闭环）

```
选剧本 → 选角色 → 开场 → 搜证 → 推理提问 → 指认凶手 → AI 复盘
```

1. **选剧本**：进入平台，看到可用剧本列表，选择一本开始。
2. **选角色**：查看每个角色的公开身份，选择自己要扮演的角色；系统给出**该角色的专属视角包**（公开身份 + 你的秘密 + 你的目标）。
3. **开场**：AI 主持人交代故事背景、人物关系、案发现场。
4. **搜证**：AI 主持按轮次发放线索卡，玩家可选择搜证方向（人物 / 现场 / 动机）。
5. **推理提问**：玩家向 AI 扮演的 NPC 提问；NPC 会**隐瞒自己的秘密、可能撒谎**，被证据戳破才会松口。
6. **指认凶手**：玩家提交「凶手 + 手法 + 动机」的判断。
7. **AI 复盘**：AI 对照真相，还原完整时间线、逐条点评玩家推理的对错与遗漏。

## 五、系统架构

```
┌─────────────────────────────────────────────────┐
│  前端 React (Vite)  —— 选剧本/选角色/聊天流/复盘面板  │
└──────────────────┬──────────────────────────────┘
                   │ HTTP + SSE（同源）
┌──────────────────▼──────────────────────────────┐
│  后端 FastAPI  —— API 路由 / 会话管理 / Agent 编排   │
│  ┌──────────────────────────────────────────┐   │
│  │  AI 层                                    │   │
│  │  · 剧本结构化抽取（LLM IE）                 │   │
│  │  · 视角隔离 Agent（NPC 视角 vs 主持视角）    │   │
│  │  · 复盘引擎（RAG + 结构化真相对照）          │   │
│  └──────────────────────────────────────────┘   │
│  ┌───────────────┐  ┌──────────────────────┐    │
│  │  SQLite       │  │  Chroma（向量）        │    │
│  │  结构化知识层   │  │  原文片段语义检索兜底   │    │
│  └───────────────┘  └──────────────────────┘    │
└──────────────────┬──────────────────────────────┘
                   │
            DashScope（通义千问 LLM + Embedding）
```

## 七、关键技术选型与「为什么」

> 每一条都从「要解决的问题」出发，而非「惯例如此」。

### 1. 后端为什么继续用 Python（FastAPI），而不是换语言
- **核心资产在 Python**：LangChain、Chroma、RAG、通义千问接入全在 Python。换语言 = 把最值钱的部分推倒重来。
- **FastAPI 的三个理由**：① 异步原生支持，SSE 流式输出顺手；② 类型提示 + 自动生成 API 文档，前端联调快；③ 能直接 import 现有 `rag.py` / `vector_stores.py`，几乎不重写 AI 逻辑，只包一层 HTTP。

### 2. 前端为什么是 React + Vite，而不是 Streamlit 或 Next.js
- **Streamlit 被放弃的原因**：单用户、session 模型、无法做账号隔离和精致交互，扛不住「公网多人访问」这个目标。
- **不选 Next.js 的原因**：本产品的交互就一个聊天流 + 几个面板，不需要 SSR / 路由 / 服务端渲染；Next.js 的工程复杂度会在一周内挤死 Agent 的开发时间。
- **React + Vite**：单页交互足够，Vite 构建快、开发体验好；「前后端分离」这个事实本身是简历可讲的点。

### 3. 流式输出为什么用 SSE，而不是 WebSocket
- 本产品的通信是**单向流**：用户输入走普通 POST，AI 输出走流式推送。没有「双向实时同步」的需求（不像真人多人在线剧本杀要房间 + 广播）。
- SSE 比 WebSocket 简单一个量级：同源无 CORS 折腾、天然支持断线重连、无需维护连接状态机。**够用就不上重的。**

### 4. 剧本知识为什么用「LLM 结构化抽取 + SQLite」，而不是只靠向量检索
- **剧本杀信息本质是结构化的**：角色、线索卡、时间线、真相是天然字段，不是「语义相近的文本块」。
- 向量检索回答不了「这个角色的秘密是什么」「还有哪些线索没发」，而这些正是游戏状态机需要精确读的。
- 用 LLM 在**摄取时一次性**把主持人手册抽成结构化 JSON，落 SQLite——这是「LLM 信息抽取（IE）」的正经工程点，可写进简历。
- **Chroma 保留做兜底**：原文分块继续进向量库，用于「开放式提问」时的语义检索（比如玩家问一个抽取时没覆盖到的细节）。

### 5. 存储为什么是 SQLite，而不是 PostgreSQL
- 一周内单服务部署，SQLite 零运维（无独立数据库进程），足够支撑结构化知识 + 游戏会话状态。
- 若后续要支撑「用户上传 + 社区」，再平滑迁移到 Postgres——数据访问层用仓库模式封装，迁移成本低。

### 6. 为什么选通义千问（qwen3-max + text-embedding-v4）
- **中文剧本理解强**：剧本杀是中文长文本、强逻辑推理场景，qwen 系列在这个场景表现好。
- **国内直连、账号现成**：已有 DashScope 接入，不新增成本。
- Embedding 与 LLM 同源，向量语义空间一致。

### 7. 部署为什么是「单服务 Docker + Railway」
- **单服务**：FastAPI 同时托管 React 的 build 产物，一个容器、一个 URL、SSE 同源，省掉 CORS 和反向代理配置。
- **Railway**：免运维、`git push` 即部署，有免费/低额度，适合一周内上线一个 demo。

## 八、数据模型（结构化 JSON）

摄取管线把主持人手册抽成如下结构（存 SQLite）：

```
Script（剧本）
├── title, description, characters_count
├── characters: [{ name, public_identity, secret, goal, relations }]
├── clues:       [{ id, category(个人/公共/现场/尸检), content, owner }]
├── timeline:    [{ time, event, is_truth }]
└── truth:       { culprit, method, motive, key_evidence }
```

视角隔离靠**字段查询**实现：
- 玩家选了角色 A → 只见 A 的 `public_identity + secret + goal`。
- AI 演 NPC 角色 B → 只见 B 的字段（B 的 `secret` 不会主动说，被证据戳破才松口）。
- `truth` 字段**只在复盘阶段注入 prompt**，游戏过程中绝不出现 → 零剧透。

---

## 九、视角隔离机制（核心难点）

```
              ┌───────────────┐
  玩家角色视角 │ 公开身份 + 秘密 │
              └───────────────┘
              ┌───────────────┐
  NPC 角色视角 │ 公开身份 + 秘密 │ ← AI 扮演时只见这个，会隐瞒/撒谎
              └───────────────┘
              ┌───────────────┐
  主持(真相)视角│ 凶手/手法/动机 │ ← 只在复盘阶段注入
              └───────────────┘
```

**防剧透原理**：剧透信息（凶手、手法、动机）在游玩阶段**根本不进入 prompt**，而不是靠「prompt 求 AI 别说」——后者不可靠，前者是结构上保证。

---

## 十、交付范围

**一周内（MVP）**：核心闭环 = 选剧本 → 选角色 → 搜证 → 推理 → 指认 → 复盘；匿名会话（无账号）。

**后续可扩展（不改变核心叙事）**：
- 用户上传剧本、热门剧本、搜索、豆瓣式「玩过」标记
- 账号体系
- 多人实时同玩（需 WebSocket + 房间）

---

## 十一、风险与应对

| 风险 | 应对 |
|---|---|
| LLM 结构化抽取不稳定 | schema 校验 + 失败降级为「纯 RAG 无视角」模式；先用格式规范的原创剧本喂管线 |
| NPC 角色一致性 / 防剧透 | 视角隔离靠字段查询（结构性保证），不靠 prompt 约束 |
| Railway（海外）访问 DashScope（国内 API）延迟 | 上线时实测延迟；必要时切换国内云服务器 |
| 公网托管商业版权剧本 | 只内置原创剧本，不托管商业版权本 |
